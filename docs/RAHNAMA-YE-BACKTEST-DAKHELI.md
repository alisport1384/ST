### ۲-۲ این اعداد از کجا آمده‌اند

نگه می‌دارد و هنگام ساخت به‌صورت خودکار نوشته می‌شود. این متادیتا **منبع حقیقت** است؛ اگر
روزی داده را دوباره ساختی، همین فایل می‌گوید چه چیزی داخل دیتاست است.

### ۲-۳ خط اول فایل چه شکلی است


یعنی: یک ردیف تیتر، بعد زمان بر حسب **میلی‌ثانیهٔ UTC**، سپس OHLC و در آخر **حجم**

### ۳-۲ چرا Release و نه داخل APK

| گزینه | APK | ایراد |
|---|---|---|
| باندل داخل APK | ≈۶٫۵ مگابایت | ۴٫۳ برابر بزرگ‌تر؛ هر آپدیت دوباره ۵ مگابایت دانلود |
| فایل جدا در Release | **≈۱٫۵ مگابایت** | فقط یک دانلود یک‌باره لازم است ✅ |

افزون بر آن، Release قابل جای‌گزینی/به‌روزرسانی مستقل از اپ است: می‌شود بعداً دیتاست
بزرگ‌تر یا بازهٔ تازه‌تر منتشر کرد بدون تغییر APK.

### ۳-۳ تأیید صحت انتشار

پس از آپلود، فایل **دوباره از GitHub دانلود شد** و هش آن با نسخهٔ محلی مقایسه شد:
هر دو `15fffd94…08db44` ⇒ فایل روی سرور سالم و کامل است.

### ۳-۴ دسترسی و هزینه

* مخزن عمومی است ⇒ دانلود **بدون توکن/ورود** کار می‌کند.
* حجم انتقال ۵٫۱ مگابایت؛ اینترنت معمولی موبایل چند ثانیه تا نیم دقیقه.
* اگر دانلود قطع شود، فایل ناقص **هرگز** جای فایل سالم را نمی‌گیرد (بخش ۵).

## ۴) محل ذخیره روی گوشی

### ۴-۱ پوشه

```kotlin
// data/Storage.kt
fun dir(ctx: Context): File {
    val ext = ctx.getExternalFilesDir(null)
    return ext ?: ctx.filesDir          // اگر حافظهٔ خارجی نبود، حافظهٔ داخلی اپ
}
```

یعنی روی گوشی:

```
/storage/emulated/0/Android/data/com.alisport.goldpin/files/
```

اگر این مسیر در دسترس نباشد (برخی دستگاه‌های قدیمی)، به پوشهٔ خصوصی اپ می‌افتد:
`/data/data/com.alisport.goldpin/files/`.

### ۴-۲ چهار فایل که در این پوشه دیده می‌شوند

| فایل | اندازهٔ تقریبی | کارش |
|---|---|---|
| `goldpin_xauusd_m1_1y.csv.gz` | **۴٫۸۹ MB** | دادهٔ یک‌سالهٔ بک‌تست (همان فایل Release) |
| `goldpin_xauusd_m1_1y.csv.gz.part` | موقت | فقط هنگام دانلود؛ بعد از تأیید هش حذف/تغییر نام می‌شود |
| `goldpin_backtest.json.gz` | **≈۳۶۰ KB** | نتیجهٔ بک‌تست: موتور + کارگزار + باکس‌ها (**بدون کندل**) |
| `goldpin_state.json.gz` | متغیر (چند MB) | وضعیت **زنده** — دست‌نخورده می‌ماند |

> نکتهٔ مهم: وجود این چهار فایل کنار هم **به‌معنای قاطی شدنشان نیست**. فایل زنده و فایل
> بک‌تست هرگز روی هم نوشته نمی‌شوند؛ هر نشست فقط فایل خودش را می‌خواند و می‌نویسد.

### ۴-۳ پاک‌کردن

* دکمهٔ **«حذف داده»** در تنظیمات: فقط فایل داده و فایل `.part` را پاک می‌کند (۵ مگابایت آزاد می‌شود).
* نتیجهٔ بک‌تست (`goldpin_backtest.json.gz`) **پاک نمی‌شود** — با اجرای قبلی همان جدول‌ها را می‌بینید.
* پاک‌کردن اپ (Uninstall) هر چهار فایل را می‌برد.
* اگر داده پاک شود ولی نشست روی «داخلی» مانده باشد، برنامه در شروع **خودکار به حالت زنده** برمی‌گردد و فایل زنده را سالم بالا می‌آورد.

## ۵) جریان کامل دانلود در اپ

```
[کاربر] «دانلود دادهٔ یک‌ساله»
        │
        ▼
۱) حذف هر .part باقی‌مانده (اگر دانلود قبلی نیمه‌کاره مانده بود)
        │
        ▼
۲) دانلود به  goldpin_xauusd_m1_1y.csv.gz.part
   • HttpURLConnection
   • connectTimeout = ۲۰ ثانیه ، readTimeout = ۶۰ ثانیه
   • گزارش پیشرفت هر ۲۵۰ میلی‌ثانیه (نه هر بایت)
   • متن نوار: «دانلود دادهٔ بک‌تست: ۴۳٪ (۲٫۱ از ۴٫۹ مگابایت)»
        │
        ▼
۳) محاسبهٔ sha256 روی همان فایل .part
        │
        ├── نامطابق ──► فایل .part حذف می‌شود
        │                پیام: «هش فایل داده مطابق انتظار نیست (دانلود ناقص) — دوباره تلاش کنید»
        │
        └── مطابق ────► ۴) rename به نام نهایی (اگر نشد: copy + delete)
                          پیام: «دادهٔ بک‌تست ذخیره شد: ۴٫۸۹ مگابایت»
```

چرا این ترتیب؟ چون اگر اپ وسط دانلود بسته شود یا اینترنت قطع شود، فقط یک فایل `.part`
ناقص روی گوشی می‌ماند و **فایل سالم قبلی دست‌نخورده** باقی می‌ماند. هش هم مانع می‌شود
فایل قدیمی/دستکاری‌شده وارد بک‌تست شود.

پارامترهای دانلود در `Feed.downloadTo()`:

| پارامتر | مقدار |
|---|---|
| `connectTimeout` | ۲۰٬۰۰۰ میلی‌ثانیه |
| `readTimeout` | ۶۰٬۰۰۰ میلی‌ثانیه |
| گام گزارش پیشرفت | ۲۵۰ میلی‌ثانیه |
| مبنای درصد | `contentLengthLong` (اگر سرور طول نداده باشد، فقط مگابایت شمارش می‌شود) |

## ۶) داده چگونه ساخته شد

ابزار: **`tools/build_sample.py`** (پایتون ۳، بدون وابستگی بیرونی).

### ۶-۱ ورودی و خروجی

```
python3 tools/build_sample.py \
    --src  /path/XAUUSD_OHLCV_1M.csv \
    --from 2025-08-21 --to 2026-08-21 \
    --out  data/goldpin_xauusd_m1_1y.csv.gz
```

### ۶-۲ پنج مرحله‌ای که فایل را «قابل‌استفاده» می‌کند

| # | کار | چرا لازم بود |
|---|---|---|
| ۱ | تبدیل ساعت فایل به **UTC** به‌صورت DST-aware (`Europe/Berlin`) | اگر انجام نشود، قواعد سشن ۲–۳ ساعت جابه‌جا می‌شوند و موتور در تعطیلات بازار معامله می‌سازد |
| ۲ | حذف کامل شنبه و یکشنبهٔ پیش از ۲۲:۰۰ UTC | همان قاعدهٔ `MarketHours` موتور؛ کندل آخر هفته نباید وارد بک‌تست شود |
| ۳ | مرتب‌سازی زمانی + حذف رکورد تکراری | فایل‌های CSV منبع همیشه مرتب نیستند |
| ۴ | اعتبارسنجی: OHLC معتبر، نبود شکاف داخلی > ۲۰ ساعت در روز معاملاتی، نبود کندل بی‌حجم | سه شکست واقعی که در بررسی داده دیده شد |
| ۵ | خروجی gzip با **همان قالب فایل نمونهٔ اپ** | پارسر موجود اپ بدون تغییر کار کند |

| همبستگی حجم دو فید | — | فقط ۰٫۶۵ | باکس‌های LV/HV بی‌معنا |

پس به‌جای «چسباندن»، دو نشست از نظر ساختاری جدا شدند.

### ۸-۲ ترتیب امن تعویض نشست

```

        ↓

        ↓
تعیین sessionMode
        ↓
بازیابی یا اجرای نشست مقصد
        ↓
ثبت sessionMode در SharedPreferences  ⇒ بعد از بستن اپ هم همان نشست برمی‌گردد
```

## ۱۰) اجرای بک‌تست داخل موتور

### ۱۰-۱ گام‌به‌گام

```
۱) خواندن فایل داده با Feed.parseCsvStream()
   • تشخیص خودکار gz از روی امضای بایت  (0x1f 0x8b)
   • خواندن خط‌به‌خط — کل ۱۸ مگابایت متن خام هرگز در حافظه ساخته نمی‌شود
   • ستون ۵ یا ۶ تایی · زمان ثانیه/میلی‌ثانیه · مرتب‌سازی و ایندکس‌گذاری یکدست
   • لاگ: «دادهٔ بک‌تست خوانده شد — کندل=۳۵۱۸۹۴ حجم‌دار=true»
        ↓
۲) بازنشانی کامل (بدون حذف فایل‌ها): کندل‌ها، باکس‌ها، کارگزار، موتور
        ↓
۳) اجرا در قطعه‌های ۲۰٬۰۰۰ کندلی
   • Engine.feed() از اندیس processed ادامه می‌دهد ⇒ نه تکرار، نه جاافتادن
   • نوار پیشرفت واقعی: «۳۲۰٬۰۰۰ از ۳۵۱٬۸۹۴ کندل»
        ↓
۴) پاس نهایی با lastIsClosed = true  ⇒ کندل آخر «بسته» حساب می‌شود
        ↓
۵) ensureCurrentTrendMarker() روی آخرین کندل بسته
        ↓
۶) ذخیرهٔ فایل نشست (بدون کندل) + لاگ زمان اجرا
```

### ۱۰-۲ چرا قطعه‌قطعه؟

اگر یک‌جا صدا زده شود، رابط برای ~۳۰ ثانیه فریز می‌شود و کاربر فکر می‌کند اپ هنگ کرده است.
با قطعه‌بندی، بین قطعه‌ها فرصت به نخ رابط داده می‌شود و درصد پیشرفت هم واقعی است.

### ۱۰-۳ سکوت کامل هنگام بک‌تست

`Alerts.inBacktest = true` در تمام مدت اجرا ⇒ **هیچ بنر، نوتیفیکیشن یا صدایی** برای
سیگنال‌های سال گذشته پخش نمی‌شود. (در حالت عادی، پرش ناگهانی ۳۵۰ هزار کندل صدها هشدار
تولید می‌کرد.)

### ۱۰-۴ یک تنظیم موتور که لازم بود

سقف آرایهٔ `times` در `Engine.kt` از **۲۰۰٬۰۰۰** به **۱٬۰۰۰٬۰۰۰** رسید؛ وگرنه هنگام پردازش
سال کامل، مارکرهای قدیمی وسط اجرا پاک می‌شدند و روند/ساختار ناقص می‌ماند.

## ۱۱) ذخیره و بازیابی نتیجه

### ۱۱-۱ چرا کندل‌ها ذخیره نمی‌شوند

| حالت | مدت اجرا | حجم فایل نتیجه |
|---|---|---|
| ۸۸٬۰۰۰ کندل (۳ ماه) | ۷٫۶ ثانیه | ۵٫۹۶ مگابایت |
| ۳۵۱٬۸۹۴ کندل **با** کندل | ۲۷٫۶–۲۸٫۵ ثانیه | ۲۲٫۰۸ مگابایت |
| ۳۵۱٬۸۹۴ کندل **بدون** کندل ✅ | ← همان اجرا | **۳۵۹٬۹۳۱ بایت** (gz) |

کندل‌ها منبعشان همان فایل داده است و در چند ثانیه دوباره خوانده می‌شوند؛ پس نگه‌داشتنشان
فقط ۲۲ مگابایت حافظه و کندی ذخیره/بازیابی می‌آورد. نتیجه: **۶۱ برابر کوچک‌تر**.

### ۱۱-۲ چه چیزی ذخیره می‌شود

* وضعیت کامل موتور: باکس‌های ساختار، LV/HV، مارکرها، رخدادها، `processed`
* وضعیت کارگزار: سفارش‌های معلق، معامله‌های باز، موجودی، سرمایه، دراودان، وضعیت مارتینگل
* باکس‌های ساختار (برای نمایش تاریخی)
* `meta`: `session` و `btSig`

### ۱۱-۳ امضای تنظیمات (`btSig`) — تشخیص «نتیجهٔ کهنه»

```kotlin
symbol / tfS / tfM / tf1 / tf2 / strategy / vpRows / vpVA / vpSmooth / distMode /
minZoneRows / maxSetups / midInvalidClose / hvScanFirstTouch / hvMarkFirstIncrease /
minTPunits / maxSlUnits / slBufTicks / entryBufTicks / slipTicks / mintick /
maxLeverage / useRiskPct / riskPct / initialEquity / mmMode / contractSize / tpUnits
```

اگر یکی از این‌ها عوض شود، هنگام بازگشت به نشست داخلی پیام می‌آید:
«⚠ تنظیمات از آخرین اجرا عوض شده — نتیجه کهنه است؛ دوباره اجرا کنید» + دکمهٔ **اجرای مجدد**.

### ۱۱-۴ گرفتن تغییرات «مود» و «استراتژی» (اصلاح v1.4.29)

سه نقطهٔ قطع اتصال پیدا و رفع شد؛ پیش از این، تغییر تنظیمات در بک‌تست اثر نداشت:

| # | ایراد | چرا بد بود | اصلاح |
|---|---|---|---|
| ۱ | `setMode()` و `setCustomTf2()` نگهبان نشست نداشتند و مستقیم `rebuild()` می‌زدند | در نشست داخلی، موتور روی دادهٔ M1 (که به‌اشتباه جای تایم‌فریم تریگر۲ گذاشته می‌شد) از نو ساخته می‌شد و نتیجهٔ بک‌تست خراب/پاک می‌شد | در نشست داخلی فقط سری نمایش دوباره تجمیع می‌شود و `backtestStale = true`؛ موتور دست نمی‌خورد |
| ۲ | بک‌تست همیشه سری **M1** را به موتور می‌داد، مستقل از `cfg.tf2` | تغییر مود تایم‌فریمی هیچ اثری روی اجرا نداشت | `internalModeSeries()` دادهٔ M1 را به تایم‌فریم تریگر۲ِ انتخاب‌شده تجمیع می‌کند |
| ۳ | `loadFromText()` تنظیمات داخل فایل زنده را روی تنظیمات فعلی می‌نوشت | با رفت‌وبرگشت بین دو نشست، استراتژی/مودِ تازه‌کاربر با نسخهٔ قدیمیِ فایل به عقب برمی‌گشت | پارامتر `applySettings`؛ فقط در شروع سرد اپ true است |

افزون بر آن:
* اگر امضای تنظیمات (`btSig`) با ذخیرهٔ قبلی نخواند، هنگام روشن‌کردن نشست داخلی **به‌طور خودکار
  بک‌تست با تنظیمات تازه اجرا می‌شود** (به‌جای نمایش نتیجهٔ مود قبلی با یک هشدار).
* `rebuild()` در نشست داخلی همیشه رد می‌شود (نگهبان نهایی) تا هیچ مسیر جانبی موتور را
  روی دادهٔ یک‌ساله خراب نکند.

ترتیب درست کار با اپ از این پس:

```
تغییر مود/استراتژی (در هر دو نشست)  →  پیام «نتیجه کهنه شد»
        ↓
«اجرای مجدد بک‌تست»  (یا خاموش/روشن کردن کلید — خودکار اجرا می‌شود)
        ↓
نتیجهٔ تازه با تنظیمات جدید
```

### ۱۱-۵ بازیابی سریع

اگر فایل نشست داخلی موجود باشد، هنگام روشن‌کردن کلید **دوباره بک‌تست اجرا نمی‌شود**؛
فایل ≈۳۶۰ کیلوبایتی خوانده و باکس‌ها/سفارش‌ها بازگردانده می‌شوند (چند صد میلی‌ثانیه).
